# Dead Alive

Dead Alive is a history trivia game built with Next.js and Prisma. The core idea is simple:

- Show the player a historical figure and a historical event.
- Ask whether the figure was alive when the event happened.
- The player answers **YES** or **NO**.
- The game changes behavior based on mode: Classic, Survival, or Timed.

## Core idea

The game is a “living history” quiz. Instead of asking what someone did or where something happened, it asks whether a person was alive at the time of an event.

That means the app combines two datasets:

- `HistoricalFigure` — people with birth and death years
- `HistoricalEvent` — events with specific years

A question is generated by pairing a random figure and event and evaluating whether the event year falls within the figure’s lifespan.

## Gameplay modes

- `CLASSIC` — one wrong answer ends the game.
- `SURVIVAL` — the player has 3 lives and can keep playing after mistakes.
- `TIMED` — the player races against a countdown timer.

## Project architecture

### Frontend

- `Next.js 16` with the App Router
- `React 19` client components for interactive game UI
- `Zustand` for local game state (score, streak, lives, settings)
- `Framer Motion` for animated transitions
- `Tailwind` / custom UI components for styling
- `sonner` for toast notifications

### Backend / database

- `Prisma` with `@prisma/client`
- `PostgreSQL` backend via Supabase
- `@prisma/adapter-pg` is used with a Postgres connection pool
- `DATABASE_URL` is used by the runtime app to connect with pooling
- `DIRECT_URL` is used by Prisma CLI / migrations in `prisma.config.ts`

The app stores:

- `HistoricalFigure` entries
- `HistoricalEvent` entries
- `Question` metadata (generated or precomputed questions)
- `User` profiles
- `GameSession` records for leaderboard history

### Database schema

The core database schema is defined in `prisma/schema.prisma`.

- `HistoricalFigure`
  - `id`: UUID primary key
  - `name`, `birthYear`, `deathYear`, `shortDescription`
  - `difficulty`: enum-like string (`EASY`, `MEDIUM`, `HARD`)
  - `tags`: string array for categorization
  - optional `birthPlace`, `deathPlace`, `imageUrl`
  - one-to-many relation to `Question`

- `HistoricalEvent`
  - `id`: UUID primary key
  - `title`, `eventYear`, `category`, `shortDescription`
  - optional `imageUrl`
  - one-to-many relation to `Question`

- `Question`
  - `id`: UUID primary key
  - foreign keys `figureId` and `eventId`
  - relation fields `figure` and `event`
  - `correctAnswer`: boolean

- `User`
  - `id`: UUID primary key
  - `username`: unique string
  - `xp`, `streak`, `highestStreak` for user progress
  - `createdAt`: timestamp
  - one-to-many relation to `GameSession`

- `GameSession`
  - `id`: UUID primary key
  - `userId`: foreign key to `User`
  - `score`: numeric score stored for leaderboard
  - `mode`: string containing `CLASSIC`, `TIMED`, or `SURVIVAL`
  - `createdAt`: timestamp

### Connection flow

The database connection is created in `src/lib/prisma.ts`.

- `dotenv/config` loads environment variables from `.env` locally.
- `DATABASE_URL` is read and passed to `pg` `Pool`.
- `PrismaPg` wraps that pool and is provided to `new PrismaClient({ adapter })`.
- In development, the code sets `NODE_TLS_REJECT_UNAUTHORIZED=0` so a self-signed Supabase cert does not block connections.
- A singleton is stored on `globalThis` to prevent multiple Prisma clients in hot reload.

Prisma CLI and migrations use `prisma.config.ts`, which points to `DIRECT_URL`.
This allows migration tools to connect separately from the runtime app and avoids pooling conflicts during schema operations.

### How questions are generated

The game is not hardcoded with static trivia. It dynamically generates question pairs by:

1. Counting available figures and events in the database.
2. Selecting a random event.
3. Choosing a figure that is either alive or not alive during that event.
4. Computing `correctAnswer` based on birth/death year comparison.

The engine is implemented in `src/lib/game-engine.ts`.

- `generateQuestion()` chooses yes/no target randomly.
- For `YES`, it finds figures whose lifespan covers the event year.
- For `NO`, it finds figures whose lifespan does not cover the event year.
- It falls back to a random figure if no qualifying figure is found.
- It returns `{ figure, event, correctAnswer }`.

### Runtime flow

- `src/app/play/page.tsx` is the play route.
- It renders `GameBoard` with mode from `searchParams`.
- `GameBoard` calls the server action `fetchNextQuestion`.
- `fetchNextQuestion()` invokes `generateQuestion()` on the server.
- The client receives the question payload and displays it.
- User answers with YES or NO, and client-side scoring logic updates state.
- On game end, `submitScore()` writes `GameSession` and potentially updates `User`.
- The `/leaderboard` page loads top sessions for the selected mode and renders the ranking.

### App router behavior

- `searchParams` is asynchronous in Next.js App Router.
- `src/app/play/page.tsx` and `src/app/leaderboard/page.tsx` both await `searchParams` before reading `mode`.
- This avoids the runtime error caused by treating `searchParams` as a synchronous object.

### Server actions and client UI

- `src/app/actions.ts` defines the `fetchNextQuestion` server action.
- `src/app/actions/leaderboard.ts` defines `submitScore()` and `getLeaderboard()`.
- `GameBoard` is a client component that manages local state and listens for question responses.
- `src/lib/store.ts` uses Zustand to preserve score, streak, lives, sound, music, and username between screens.

### Security and deployment

- On Vercel, `DATABASE_URL` must be set as an environment variable.
- `NODE_TLS_REJECT_UNAUTHORIZED=0` is only safe as a temporary workaround in development/staging when the database uses a self-signed cert.
- For production, use a valid SSL certificate chain or a managed DB connection that supports trusted TLS.

### Practical extension points

If you want to change how the game works, these are the main places to edit:

- `prisma/schema.prisma` to change data shape or add new tables
- `src/lib/game-engine.ts` to change question generation rules
- `src/components/game/GameBoard.tsx` to change scoring, UI, or mode logic
- `src/app/actions/leaderboard.ts` to change how scores are stored or filtered
- `src/lib/prisma.ts` to change the runtime connection setup

### Data model notes

- `Question` can be used for precomputed/seeded question pairs, but current runtime generation does not require stored rows.
- `GameSession` is the source of truth for leaderboard results.
- `User.username` is enforced as unique so player identities can be reused safely.

### Recommended editing workflow

1. Open `prisma/schema.prisma` to inspect tables.
2. Change or extend the schema.
3. Run Prisma migrate or `prisma db push`.
4. Update `src/lib/game-engine.ts` if question logic changes.
5. Update `src/components/game/GameBoard.tsx` if the UI or mode rules change.
6. Test locally with `npm run dev`.

## Developer Bible: end-to-end component map

This app is a complete end-to-end stack. Use this section as your blueprint for replicating it.

### 1. User interface and routing

- `src/app/page.tsx` — home screen or launch page.
- `src/app/play/page.tsx` — the main game route. It reads `searchParams.mode` and renders `GameBoard` for the selected mode.
- `src/app/leaderboard/page.tsx` — leaderboard route. It fetches leaderboard data and renders score history.

### 2. Game UI and state management

- `src/components/game/GameBoard.tsx` — the interactive game component.
  - loads questions by calling the server action `fetchNextQuestion()`.
  - displays current score, streak, lives, timer, and question.
  - handles player answers and game-over behavior.
  - submits scores via `submitScore()`.

- `src/lib/store.ts` — shared client state with Zustand.
  - stores game values like `score`, `streak`, `lives`, `username`, `soundEnabled`, and `musicEnabled`.
  - persists some settings to `localStorage`.
  - provides helper actions for score updates and audio.

### 3. Question generation and game engine

- `src/lib/game-engine.ts` — the brain of the game.
  - generates random questions using database rows.
  - decides whether the correct answer should be YES or NO.
  - chooses a random event and a corresponding figure.
  - calculates truth using birth/death years.
  - exports `generateQuestion()` for server actions.

### 4. Server actions and API boundary

- `src/app/actions.ts` — server action for gameplay questions.
  - exports `fetchNextQuestion()`.
  - this runs on the server and calls `generateQuestion()`.

- `src/app/actions/leaderboard.ts` — server actions for score submission and leaderboard queries.
  - `submitScore()` inserts or updates user records and creates `GameSession` entries.
  - `getLeaderboard()` loads top sessions for the selected mode.

### 5. Database schema and storage

- `prisma/schema.prisma` — database schema definition.
  - `HistoricalFigure` stores people, lifespan, descriptions, and difficulty.
  - `HistoricalEvent` stores events and event years.
  - `Question` stores question pairs and answers, but this app currently generates questions dynamically.
  - `User` stores player identity and XP/streak data.
  - `GameSession` stores leaderboard records.

### 6. Database connection setup

- `src/lib/prisma.ts` — runtime database client.
  - uses `dotenv/config` to load `.env` locally.
  - reads `DATABASE_URL` and creates a `pg` `Pool`.
  - wraps the pool with `PrismaPg`.
  - creates a singleton `PrismaClient` to avoid duplicate connections in development.
  - temporarily disables TLS certificate validation in local development when using a self-signed cert.

- `prisma.config.ts` — Prisma CLI configuration.
  - points migrations to `DIRECT_URL` instead of the pooled runtime URL.
  - ensures `prisma migrate` and `prisma db push` use a direct database connection.

### 7. Deployment path

- Deploy the app to Vercel.
- Set environment variables in Vercel: `DATABASE_URL`, `DIRECT_URL`, and any other required secrets.
- The frontend will request server actions from the deployed Next.js server.
- The server will connect to Supabase/Postgres using Prisma.

### 10. How data flows in one play session

1. User opens `/play?mode=CLASSIC`.
2. `play/page.tsx` awaits `searchParams`, reads mode, and renders `GameBoard`.
3. `GameBoard` calls `fetchNextQuestion()`.
4. `fetchNextQuestion()` runs on the server and calls `generateQuestion()`.
5. `generateQuestion()` queries the database via Prisma and returns a question payload.
6. `GameBoard` displays the figure, event, and answer buttons.
7. The player selects YES or NO.
8. `GameBoard` updates score/streak locally via Zustand.
9. If the game ends, `submitScore()` saves the result to the database.
10. The player can view `/leaderboard?mode=CLASSIC` to see scores.
